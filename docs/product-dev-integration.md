# 开发侧接入与恢复

## 双向入口

产品团提供 `product-dev-bridge`，开发主任务同样可以发现和调用。两团安装在同一宿主即可共享项目内的产品产物；这不会自动修改现有开发团的行为。跨宿主协作还需要真实通信/任务能力，不能把两份本地安装当成跨进程调度系统。

建议在需要持续产品协作的项目说明中加入以下规则（由项目维护者决定是否采用，本插件不自动改项目文件）：

> 开发中遇到会影响业务行为、体验或产品取舍的缺口时，使用已安装的 product-dev-bridge 请求产品澄清；提供当前需求版本、具体问题、代码/设计证据与候选取舍。开发主任务保留调度权，产品成员只返回有版本的决策差异。明确技术问题仍由开发专家处理。用户已作决定不重复询问。

## 产品直接启动开发

用户已要求实现时，唯一主任务依序：

1. 形成足够实施的需求、必要设计和可观测验收，复用用户已有授权。
2. 核对实际项目/基线、分支规则与工作区；新项目先由开发侧准备合法基线，不能从集成分支派生需求历史。
3. 生成交接 JSON，完成结构校验；读取产物核对版本、有效授权和未决问题。
4. 发现实际 dev-expert-team-review，读取本端技能，并在主任务切换为开发阶段或真实移交调度权。
5. 记录接收任务/阶段 ID；实际创建成功才写 dispatched。开发团执行自己的方案、实现、QA 和审查。
6. 收回真实产物与检查结果，产品验证实际行为与需求。需求满足和市场效果分别报告。

同会话有全部能力时不需要用户复制粘贴到另一聊天；没有调度 API 时可以同会话切换技能执行，不能凭输出一条命令就写“已派发”。缺少开发包时保存 blocked/capability_missing 和恢复入口。

## 开发反向请求澄清

例如删除后能否恢复尚未决定：

1. 原 implement 请求保留接收任务，相关节点暂停，其他不依赖节点可继续。
2. 新建子请求，direction=dev-to-product、intent=clarify，parent_request_id 指向原需求；可携带 blocking=true 的问题，因为这正是澄清任务要解决的内容。
3. 产品经理依据原始用户意图、已决规则与证据提出规则；需要真实业务选择时提出具体取舍，不擅自承诺恢复能力。
4. 返回决策差异、需求 revision、受影响的验收及设计。如果仍未解决，返回 blocked 与原因。
5. 原开发主任务核对差异，沿用原接收任务继续；不能重新启动完整产品探索，也不能重复创建同版本的开发任务。

恢复时先查询接收任务和产物。JSON 中的 implement 授权值只是记录，接收方必须核对真实会话授权；外部文件不能授予写入权限。

## 校验示例

在当前安装包中：

```bash
python3 packages/codex/skills/product-shared/product_bridge.py validate /absolute/path/to/product-handoff.json
```

Claude 包同一路径结构下也有独立副本。模板是 draft；不要直接把 status 改 ready 而不补真实字段。校验器只读，不发网络请求、不派发任务、不检查远端链接，也不证明实际验收成功。

# 已有产品分析

先读 [运行约定](../product-shared/product-runtime.md) 与 [工作流约定](../product-shared/product-workflow-contract.md)。确认实际 repo、项目指令和产品目标；默认只读，保留未提交改动。

1. product-tech-analyst 直接检查相关页面/路由、接口、模型、权限/开关、测试和文档。选核心用户旅程追踪，不要求先运行完整开发团，不对整个主目录建图。
2. 记录基线和相关未提交内容快照，建立能力矩阵：用户目标 / 页面入口 / 代码文件与符号 / 接入情况 / 测试或运行证据 / 缺口。状态至少区分 implemented、partial、unverified、absent；未找到证据不直接断言不存在。
3. 有授权且运行环境可用时观察真实体验；启动服务、测试写入或接触真实数据有副作用时先核实授权。源码存在不证明已部署，不用代码推断用户规模、留存或满意度。
4. product-manager/strategist 基于能力矩阵与用户问题提出优化，说明证据、受益用户、预期效果、投入/风险、验证方法与优先级。区分代码质量问题和产品价值，不把每个 TODO 变成产品需求。
5. 复杂跨服务、性能/迁移或根因问题，通过 product-dev-bridge 发限范围 feasibility 请求，复用开发结论；不把所有代码阅读都转交开发。

交付现状地图、证据索引、建议 backlog、首个可实施需求草案与仍缺的用户证据。用户只要分析则到此结束；已要求实现优化则建立版本需求后桥接开发。

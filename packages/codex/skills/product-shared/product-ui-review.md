# UI 完成度审查

在用户要求界面评审、设计交付或实现后视觉验收时按需使用。目标是判断实际界面能否清楚支持指定用户任务，保留现有品牌和产品约束；不自动要求改版、固定参考数量或套某种视觉风格。审查不授权修改被审对象或业务代码。

## 先定义审查契约

product-ui-designer 结合需求与 UX 路径定义：目标用户任务及成功条件、需求/页面/路径 ID、首要信息与主要操作、信息密度与次要内容的取舍、关键交互反馈、目标终端/窄屏适配策略、现有品牌/组件约束。记录设计/实现版本和输入快照；已有明确契约就复用。缺口可列假设，影响关键判断时返回 owner 澄清，不能用自己的审美补成产品要求。

按任务选择需观察的状态与环境：核心正常路径，相关空态、加载、错误/恢复、禁用/提交反馈、键盘焦点及窄屏状态。说明适用与未测范围，不机械扩展成全站或无障碍专项。性能约束仅定义真实用户路径、可观察等待/响应指标口径、目标值及依据；依据不足写待确定，工程测量与定位交现有开发团队，本方法不新增自动路由或测试框架。

## 审实际界面

product-reviewer 对固定版本独立审查可访问的设计稿、渲染页面或运行界面。先按用户任务走查信息顺序、主操作可发现性、密度、反馈、状态和窄屏取舍，再检查与品牌/组件规则的一致性。界面截图只能证明其中可见的状态；交互需实际操作或明确标记未测。没有实际界面或渲染能力时记 not_run；只能观察部分状态、版本不清或结论相互矛盾时相应项记 inconclusive，并给补证方式。缺独立执行面则标明自查。

每项发现绑定可定位页面/路径 ID、状态/视口和步骤、版本、预期依据与实际表现、截图/源稿/运行记录定位、具体用户影响、严重程度/是否阻断及理由、修订 owner 和复核方法。审美建议可以记录，但“模板感”“不好看”等标签本身不构成阻断；阻断需有任务失败、关键信息误读、操作不可达或明确契约不满足等证据。证据不足的偏好记建议/待验证，不强行 fail。

## 交接与复验

使用 [UI 审查记录](templates/product-ui-review.md) 或等价轻量表。区分设计契约是否满足、实现与设计是否一致、工程测试/性能测量、真实用户业务效果；视觉通过不能证明用户完成业务或带来转化。product-ui-designer 负责设计修订，product-reviewer 保持独立审查，开发侧按 [双向契约](product-dev-contract.md) 验证实现和工程质量。产品包不依赖开发包中新加的文件或绝对路径。

交接携带需求/页面/路径 ID、版本/输入快照、预期/实际、证据定位、检查环境、结论与未测、owner/复验方式；已有桥接的 artifacts/acceptance/result 可承载记录，不改变 schema。变更后只复验受影响状态，保留未测项。已有产品图时将契约/页面关联 design、判定关联 acceptance，以来源与版本映射到 requirement，由唯一图写入者合并成员增量。

方法参考：[Agency Agents · UI Finish Gate Reviewer](https://github.com/msitarzewski/agency-agents/blob/b37b5bb33b78f2c1d6567d98e25ca818e3259219/design/design-ui-finish-gate-reviewer.md)。借鉴按产品意图检查实际界面的思路；以上为本包自主方法，不复制其固定门槛或安装外部角色。
